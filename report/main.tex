\section*{Abstract}
%% ---------------------------------------------------------------------
PowerShell is an automation tool that is available in all versions of Windows. The reason why adversaries use PowerShell is its reliability, features, and execution of code in memory without writing to the disk. This case study examines how PowerShell has been used in real attacks, including the Odinaff attacks on banks, the POSHSPY backdoor of the APT29 group, the Emotet malware campaigns and the REvil ransomware attack through Kaseya VSA. These cases show that traditional signature-based antivirus finds it hard to catch such scripts, because attackers can easily change the text of a script while keeping its behaviour the same. Based on the lessons from these cases, we built and tested a machine-learning system that reads a PowerShell script, decides whether it is malicious, and takes an automatic response according to its risk. Using the public MPSD dataset, from which more than half of the malicious files had to be removed as duplicates, an ensemble model achieved an F1-score of 0.972, detecting 96.2\% of malicious scripts while wrongly flagging only 0.7\% of benign scripts. In a test on unseen scripts, the automatic response system contained 91.2\% of malicious scripts and wrongly blocked only 0.23\% of benign ones. The study shows that explainable machine learning combined with a careful, human-supervised response policy can help organisations defend against PowerShell attacks.

\vspace{0.3cm}
\noindent\textbf{Keywords:} PowerShell, fileless malware, case study, machine learning, malware detection, automated incident response, ransomware, MITRE \attck{}.

\section{Introduction}
%% ---------------------------------------------------------------------
PowerShell is a command-line shell and scripting language made by Microsoft. It is installed by default on Windows and is used by system administrators to automate everyday tasks such as managing users, installing software and changing settings. Because it is powerful and already trusted on the system, attackers also like to use it. With a single PowerShell command, an attacker can download harmful code from the internet and run it directly in memory, without saving any file on the disk. This type of attack is called a \emph{fileless} or \emph{living-off-the-land} attack, because the attacker uses tools that are already present on the computer~\cite{wueest2017}.

PowerShell attacks remain a serious and current problem. Symantec reported that 95.4\% of the PowerShell scripts submitted to its analysis service were malicious~\cite{wueest2016}. MITRE \attck{}, a widely used knowledge base of attacker behaviour, lists PowerShell as technique T1059.001 and records its use by many criminal and state-sponsored groups~\cite{mitre_t1059}. The 2025 Threat Detection Report by Red Canary found that command and scripting interpreters were the most common attack technique for the sixth year in a row~\cite{redcanary2025}. Removing PowerShell is not possible, because organisations depend on it; in 2022 the NSA and CISA advised organisations to keep PowerShell but to log and monitor it carefully~\cite{nsa2022}.

Logging alone, however, only collects data. Someone still has to decide whether each script is safe or harmful, and do so quickly enough to stop an attack. Attackers make this harder by disguising their scripts with free tools such as Invoke-Obfuscation~\cite{bohannon2016}, and security teams already receive more alerts than they can check~\cite{hassan2019}. Machine learning can help by scoring every script automatically and supporting a fast and consistent response, in line with current incident-response guidance~\cite{nist2025}.

\head{Problem statement.} Given the text of a PowerShell script captured on a Windows computer, the system should (1) decide whether the script is malicious, with very few false alarms, and (2) automatically take a suitable action, such as raising an alert or blocking the script, while leaving the most serious actions to a human analyst.

\section{Case Study: PowerShell in Real-World Attacks}
%% ---------------------------------------------------------------------
This section looks at why attackers choose PowerShell, how a typical attack unfolds, and what four well-documented incidents teach defenders.

\head{Why attackers choose PowerShell.} PowerShell offers attackers several advantages at once. It is already installed and trusted, so running it does not look unusual. It can call almost any Windows function and .NET library, which allows it to download files, read passwords, change security settings and talk to remote servers. It can run code that exists only in memory, which leaves little evidence on disk for antivirus to scan. Finally, scripts can be encoded or disguised in many ways, so the same attack can look completely different each time~\cite{wueest2016}, \cite{bohannon2016}. In earlier years, detailed PowerShell logging was also turned off by default in most organisations, so attackers could often act without leaving a record~\cite{wueest2016}.

\head{A typical attack chain.} Figure~\ref{fig:chain} shows how PowerShell commonly appears in an attack. The attacker first gains entry, often through a phishing email with a malicious document. When the victim opens the document, a hidden macro starts PowerShell, which downloads the next stage of the attack (\attck{} T1105) and runs it in memory (T1059.001, T1620). The attacker then sets up a way to come back later (persistence), steals passwords (T1003), turns off security tools (T1562) and spreads to other computers. The final goal may be data theft, financial fraud or ransomware. PowerShell can be involved at almost every stage, which means that monitoring it gives defenders many chances to stop the attack.

\head{Case 1: Odinaff attacks on financial organizations in 2016.} Symantec reported in 2016 on a series of targeted attacks against financial institutions, including banks, securities, and trading companies as well as payroll providers around the world, which were carried out using a Trojan dubbed Odinaff~\cite{symantec2016odinaff}. The Trojan was delivered using malicious Word macros, password-protected files, and existing botnets. Once inside the network, the hackers used lightweight hacking tools like Mimikatz along with legitimate utilities like PowerShell to explore the network and find important systems; some of the organizations affected were part of the SWIFT financial messaging network. Here, we see how cybercriminals leverage PowerShell alongside password stealing tools for stealthy network reconnaissance because the legitimate use of an administrative tool is, by itself, suspicious-free.

\head{Case 2: APT29 and the POSHSPY backdoor (2015--2017).} According to Mandiant, POSHSPY is a backdoor deployed by the state-sponsored APT29 in case their main tools got detected~\cite{dunwoody2017}. The POSHSPY malware was solely written in PowerShell and WMI. The encrypted PowerShell script was located in a custom WMI property and not in the file while the WMI event subscription ensured automatic restarts. This malware had the ability to download and execute other scripts and programs while connecting to its command and control servers rarely using legitimate local websites. Mandiant stated that because all processes used were legitimate, the malware could only be seen through enhanced logging or memory forensics. This is a clear example of why PowerShell logging is vital since without such logging, fileless malware can stay undetected for a very long time.

\head{Case 3: Emotet malware campaigns 2014 onwards.} The Emotet malware initially started as a banking Trojan and has become one of the most widespread malware families in the world, often serving as a vector for other malicious software, including ransomware. In October 2020, CISA warned of an increase in the number of Emotet phishing attacks targeted at state and local governmental organizations, indicating that Emotet spreads inside the network via guessing passwords and replication onto the shared drives~\cite{cisa2020emotet}. Many instances of Emotet campaigns used Word documents containing macros that ran an obfuscated PowerShell script, which retrieved the malware from a remote server. Analyzing PowerShell droppers used in the Emotet campaigns, Patsakis et al.\ discovered that they were highly obfuscated, and even the best language models could not reveal the download URLs of the hidden files~\cite{patsakis2024}.

\head{Case 4: REvil ransomware through Kaseya VSA (2021).} On 2 July 2021, the affiliate of REvil ransomware gang leveraged the vulnerabilities in Kaseya VSA, the software used for managing remote access by managed services providers, and released the malicious update to the clients' computers, thereby affecting hundreds of companies in a single day~\cite{sophos2021}. Since the management agent was running at high privileges, the attackers used the PowerShell command to turn off Microsoft Defender real-time protection and script scanning prior to launching ransomware~\cite{splunk2021}. Thus, this example shows how fast modern attacks can spread -- only one malicious update infected hundreds of companies in one day without much room left for manual analysis.

\head{Comparing the cases.} Although the four incidents had different goals, they share a common pattern. The attackers were of very different types: a financially motivated criminal group (Odinaff), a state-sponsored espionage group (APT29), a large criminal malware operation (Emotet) and a ransomware affiliate (REvil). Their priorities also differed. APT29 valued stealth and long-term access, so POSHSPY was designed to run rarely and to blend in with normal traffic. REvil valued speed and scale, so its PowerShell activity was short and direct, focused on disabling defences just before the ransomware ran. Emotet relied on volume, sending very large numbers of emails with disguised scripts, while Odinaff relied on careful exploration of a small number of selected networks. In every case, however, PowerShell was chosen because it was already present, trusted and capable, and in every case the malicious activity left traces in the scripts that ran. Mapped onto Figure~\ref{fig:chain}, Emotet appears mainly at the execution and download stages, APT29 at the in-memory payload and persistence stages, Odinaff at the credential-theft and network-exploration stages, and REvil at the defence-evasion stage just before impact. A defensive system that examines every script, instead of looking for one particular tool or stage, therefore has a chance to interrupt very different kinds of attack.

The table also shows a gap: logging and scanning produce evidence, but none of these controls by itself decides quickly whether a particular script is malicious and what to do about it. This gap is the focus of the system developed in this study.

\head{Lessons from the cases.} Table~\ref{tab:cases} summarises the four cases. Together they lead to five requirements for a defensive system, which guide the rest of this study:
\begin{enumerate}
  \item \textbf{Use the logs Windows already produces.} Script Block Logging and AMSI record the actual code that runs, including code that was hidden or downloaded at run time~\cite{ms_logging}, \cite{ms_amsi}.
  \item \textbf{Look at behaviour, not exact text.} Since scripts can easily be hidden, detection must depend on characteristics that will withstand any slight changes.
  \item \textbf{Keep false alarms very low.} Admins use PowerShell for their day-to-day tasks; therefore, a detection system that inhibits the normal processes of admins will be regarded with suspicion.
  \item \textbf{Respond automatically and quickly.} Ransomware spread is quick, calling for regular operations to be done without waiting for human assistance.
  \item \textbf{Explain every decision.} The alerts must be set to reflect the purpose of the script being executed, e.g., based on \attck{}~\cite{strom2018} terminology.
\end{enumerate}

\section{Literature Review}
%% ---------------------------------------------------------------------
Microsoft has added security features to PowerShell that make detection possible. \emph{Script Block Logging} records the text of every script that runs as Windows Event ID 4104~\cite{ms_logging}, and the \emph{Antimalware Scan Interface} (AMSI) allows antivirus software to scan a script just before it runs~\cite{ms_amsi}. The MITRE \attck{} framework provides a common language to describe attacker behaviour~\cite{strom2018}.

Because attackers disguise their scripts, much research has focused on obfuscation. Bohannon showed that a single command can be rewritten in many forms~\cite{bohannon2016}, and Bohannon and Holmes built Revoke-Obfuscation, which detects disguised scripts using statistical features~\cite{bohannon2017}. Several tools try to remove the disguise before analysis, including PowerDrive~\cite{ugarte2019}, the method of Li et al.~\cite{li2019} and its extension by Xiong et al.~\cite{xiong2022}, PowerDP~\cite{tsai2023} and PowerPeeler~\cite{li2024}.

Machine learning has been applied to detect malicious PowerShell directly. Hendler et al.\ trained deep neural networks on more than 66,000 PowerShell commands and found that combining two different models gave the best results~\cite{hendler2018}. In later work they used AMSI data and reached a detection rate of nearly 90\% with less than 0.1\% false alarms~\cite{hendler2020}, and Microsoft described using such models in its Defender products~\cite{ms_blog2019}. Rusak et al.\ used the syntax tree of scripts~\cite{rusak2018}, Song et al.\ compared token-based and tree-based features and reported about 98\% detection~\cite{song2021}, and Mimura and Tajiri used word embeddings~\cite{mimura2021}. Fang et al.\ combined several types of features with a random forest, reported 98.93\% accuracy and released the MPSD dataset used in this study~\cite{fang2021}. Saxe and Berlin showed that character-level models work well for short security texts such as web addresses~\cite{saxe2017}, and general reviews of machine learning for malware are given by Ucci et al.~\cite{ucci2019} and Gibert et al.~\cite{gibert2020}. The newest work uses large language models to both detect and explain malicious PowerShell~\cite{wang2026}.

Researchers have also warned that machine-learning results in security can look better than they really are. Sommer and Paxson explained why intrusion detection is harder than ordinary classification~\cite{sommer2010}. Arp et al.\ listed common mistakes, such as allowing very similar samples to appear in both training and test data~\cite{arp2022}, and Pendlebury et al.\ showed that careless data splitting can make malware detectors appear much more accurate than they are~\cite{pendlebury2019}. Concerning the response aspect, SOAR technologies are used to bind the detection process with the action~\cite{islam2019}, while provenance-based techniques support analysts in dealing with a huge number of alerts~\cite{hassan2019}, \cite{hassan2020}.

Table~\ref{tab:lit} is a list of some important studies. Most previous studies have focused solely on the detection aspect with highly accurate rates of performance. However, very few of them have analyzed duplicates within their datasets, and still fewer have incorporated detection with the response action.

\section{Methodology}
%% ---------------------------------------------------------------------
The proposed system follows the five requirements identified in the case study. It works in six steps, shown in Figure~\ref{fig:flow}: scripts are collected from Windows logs, the data is cleaned, features are extracted, a machine-learning model gives each script a risk score between 0 and 1, a response policy chooses an action, and every decision is recorded.

\begin{figure}[htbp]
\centering
\begin{tikzpicture}[font=\small,
  box/.style={draw=black, thick, rounded corners=3pt, fill=white, align=center, text width=3.6cm, minimum height=1.5cm},

  \node[box] (a) {\textbf{1. Collect scripts}\\ Windows Event ID 4104};
  \node[box, right=0.9cm of a] (b) {\textbf{2. Clean data}\\ remove duplicates};
  \node[box, right=0.9cm of b] (c) {\textbf{3. Extract features}\\ text and behaviour};
  \node[box, below=1.0cm of c] (d) {\textbf{4. ML model}\\ risk score (0--1)};
  \node[box, left=0.9cm of d] (e) {\textbf{5. Response policy}\\ choose an action};
  \node[box, left=0.9cm of e] (f) {\textbf{6. Act and record}\\ alert, block, log};
  \draw[arr] (a) -- (b); \draw[arr] (b) -- (c); \draw[arr] (c) -- (d);
  \draw[arr] (d) -- (e); \draw[arr] (e) -- (f);
\end{tikzpicture}
\caption{Workflow of the proposed system}\label{fig:flow}
\end{figure}

\head{Dataset.} We used the public MPSD dataset released by Fang et al.~\cite{fang2021}. It contains 4,202 malicious scripts, 4,316 benign scripts and 4,202 ``mixed'' scripts in which malicious code is hidden inside a normal script. The malicious scripts include downloaders, shellcode loaders, reverse shells and password-stealing tools, similar to those seen in the cases above. The benign scripts are normal administration scripts. All malicious scripts were handled only as text and were never run.

\head{Data cleaning.} Before training, the data was checked for problems, as recommended by Arp et al.~\cite{arp2022}. Only 1,875 of the 4,202 malicious files were unique, which means 55.2\% were exact copies; duplicates were removed. Twelve files appeared in both the malicious and benign folders and were removed because their true label is unknown. A special byte-order mark appeared at the start of about 35\% of benign files but never in malicious files; since a model could learn this meaningless pattern, it was removed from all files. Finally, many malicious scripts differ only in variable names or numbers, so such near-copies were grouped into ``families'' (816 families for 1,875 malicious scripts), and a family was never split between training and testing. After cleaning, 1,875 malicious and 4,302 benign scripts remained.

\head{Feature extraction.} Each script is converted to lower case and the backtick character is removed, because PowerShell ignores both and attackers use them to disguise commands. Two kinds of features are then extracted. The first are \emph{text features}: the script is split into short sequences of 3 to 5 characters, and each sequence is weighted with TF-IDF~\cite{salton1988}, so that a sequence that is frequent in one script but rare in others receives a high weight:
\begin{equation}
  \text{TF-IDF}(t,d) = \text{tf}(t,d) \times \log\frac{N}{\text{df}(t)},
\end{equation}
where $\text{tf}(t,d)$ is how often sequence $t$ appears in script $d$, $N$ is the number of scripts and $\text{df}(t)$ is the number of scripts containing $t$. The second are 33 \emph{behaviour and statistical features}, such as script length, number of lines, randomness of characters and counts of suspicious keywords. The keywords are grouped by attacker behaviour and linked to \attck{}, for example downloading tools (T1105), running code (T1059.001), code injection (T1055) and disabling defences (T1562), which are the same behaviours seen in the case study.

\head{Machine-learning models.} Four models and one ensemble were trained with the scikit-learn library~\cite{pedregosa2011}: logistic regression (LR) on the text features, LR on the behaviour features as a simple baseline, a random forest (RF) of 300 decision trees~\cite{breiman2001}, and a gradient boosting model (HGB) similar to LightGBM~\cite{ke2017}. The ensemble averages the scores of the text-based LR and the behaviour-based RF; because the two look at different evidence, combining them makes the result more stable. Deep learning was not used because the dataset is small and simpler models are faster and easier to explain.

\head{Evaluation.} The models were tested with five-fold cross-validation~\cite{kohavi1995}: the data is split into five parts, and each part is used once for testing while the other four are used for training. Families of near-copies were always kept in the same part, so a model is never tested on a script it has almost seen before. With TP, FP, TN and FN denoting true positives, false positives, true negatives and false negatives, the main measures were:
\begin{equation}
  \text{Precision} = \frac{TP}{TP+FP},\qquad \text{Recall} = \frac{TP}{TP+FN},\qquad F_1 = \frac{2 \times \text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}.
\end{equation}
Accuracy and the area under the ROC curve (AUC) were also reported.

\head{Automated response.} The risk score is used to choose one of four actions (Table~\ref{tab:tiers}). Less harmful actions are taken automatically, while the most serious action, disconnecting a computer from the network, needs a human analyst's approval. Every decision is saved in a log together with the \attck{} techniques found, and suspicious web addresses are written in a safe form (for example, \texttt{hxxp} instead of \texttt{http}).

\section{Implementation Details}
%% ---------------------------------------------------------------------
The system was written in Python 3.13 using scikit-learn for machine learning, pandas and NumPy for data handling and Matplotlib for graphs, and it was run on an ordinary computer with a 4-core processor and 15 GB of memory, without a GPU. This program consists of four modules: data, which cleanses data set; features, which calculates textual and behavioral features; model, which trains and tests models; and response modules. Response module gets input from Windows Event ID 4104 data and calculates risk score from model, response level from this risk score, related \attck{} technique and makes record in log. For security reasons, this module runs in ``dry-run'' mode, where actions are simulated but not performed. In a real business environment, Script Block Logging would be enabled by Group Policy~\cite{ms_logging}; logs will be transferred to the central server for risk scoring, and the response module will interact with company's security infrastructure. Seven unit tests check the key functionality, and all the tests pass successfully.

\head{Effect of eliminating duplicate records.} Upon running the ensemble on data containing duplicate records with a simple random partition, the F1-score of the algorithm increased to 0.988, and the percentage of missed malicous scripts decreased to 1.7\%. This increase in the value can be deceiving, since the algorithm was partially trained on scripts that it was supposed to encounter again in the future. In this case, without cleansing, the actual number of attacks missed would be overestimated by more than half, in accordance with the remarks by Arp et al.~\cite{arp2022} and Pendlebury et al.~\cite{pendlebury2019}.

\head{Malicious code hidden inside normal scripts.} Malicious code that is embedded within an otherwise legitimate script. This problem became obvious in testing the models on the ``mixed'' scripts, which have a malicious code embedded into a long legitimate script, similar to the Emotet's ``dropper'' disguise. This became the primary vulnerability of the ensemble, which could identify 46.7\% of such cases. The reason was that there was a lot of legitimate code covering up for the relatively small malicious part of it. Adding examples of mixed scripts to the training dataset increased detection rate up to 96.4\%, while causing only a slight increase in false positives (0.70\% to 1.05\%).

\head{Automated response results.} To test the complete system, the ensemble was trained on four parts of the data, and the fifth part (1,233 scripts it had never seen) was sent through the response system as Windows log events. Table~\ref{tab:response} shows the outcome. Most malicious scripts were stopped automatically, very few benign scripts were blocked, and a typical script was processed in about 91 milliseconds, which is fast enough to act before an attack like the REvil case can spread. The most common attacker behaviours found were running code with PowerShell (T1059.001), loading code into memory (T1620), code injection (T1055) and downloading tools (T1105), the same stages shown in Figure~\ref{fig:chain}.

\head{Illustrative walkthrough: an Emotet-style infection.} To show how the parts of the system work together, consider an employee who opens an infected invoice document, as in the Emotet campaigns. The following sequence describes the intended behaviour of the system; it is an illustration based on its design, not a recorded incident.
\begin{enumerate}
  \item In the document, the macro invokes PowerShell to execute the command that is encoded. When executed, Windows decodes the command and logs the decoded script as event id 4104.
  \item It takes the event after seconds and then analyzes its features. Both encoding (T1027) and downloading (T1105) indicators are available, and the textual features are similar to those of the known downloaders, resulting in a high risk score.
  \item Since the value is greater than 0.70, the script becomes contained as the powershell process is terminated, the file is quarantined and its download location blocked, ensuring that the next stage of the malware never downloads.
  \item The security team will receive an alert that will contain the score, the \attck{} technique used, and the blocked address. Should the presence of code injection and credential theft have been observed with an extremely high score, then computer isolation will be recommended, pending the analyst's approval.
\end{enumerate}
This walk-through highlights how the lessons learned from the case study (use current logs, consider the behavior, react fast, and explain each decision) can be seen in the system's architecture.

\head{Limitations.} Some limitations exist in the research. It uses just one publicly available database; therefore, further verification is required by performing tests using the actual data of enterprises. The proposed solution analyzes only the text of the script and not additional information about it, such as which application runs this script, which may be useful in cases like Odinaff, when legal software is misused.

This case study explored the application of PowerShell by attackers and the possibilities of using machine learning in order to prevent the corresponding cyber attacks. Four cases -- Odinaff, APT29, Emotet and REvil -- demonstrated how attackers exploit PowerShell at all stages of attacks, disguise the scripts in order to make them signature-less, and do significant harm within seconds. Based on this analysis, a system which ranks PowerShell scripts based on Windows logs and automatically provides a response was developed. As a result of removing duplicates and mislabeled data from the MPSD dataset, an ensemble of a text-based logistic regression and a behavior-based random forest achieved the F1-score of 0.972 and detected 96.2\% of malicious scripts while producing false alarms only in 0.7\%. For an out-of-sample test, the response system managed to prevent 91.2\% of malicious scripts, made mistakes blocking 0.23\% of benign scripts and required 91 milliseconds per one script. Two more lessons were obtained. First, it was found that duplicate detection is required when working with the dataset to avoid the illusion of high-quality results. Second, malicious scripts embedded into the legitimate ones require special training samples. For future research, the following steps are recommended. The system can be applied to company logs, integrated with AMSI in order to prevent execution of suspicious scripts, provided with data about currently running processes and combined with the large language models providing explanations for the alerts~\cite{wang2026}. Thus, explainable machine learning combined with proper response policy constitutes the efficient defense against PowerShell attacks which correspond to expert recommendations to control PowerShell~\cite{nsa2022}.
