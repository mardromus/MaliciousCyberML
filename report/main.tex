\section*{Abstract}
\addcontentsline{toc}{section}{Abstract}
PowerShell is installed by default on every supported version of Windows, and the capabilities that make it valuable to system administrators, namely direct access to the .NET runtime and Windows APIs, in-memory execution and remote management, also make it one of the most frequently abused tools in intrusions that ``live off the land''. Signature-based defences detect such scripts poorly, since a payload can be renamed, re-encoded or fragmented without any change in behaviour. This report presents the design, implementation and evaluation of a machine-learning pipeline that classifies PowerShell script blocks as malicious or benign and uses the resulting risk score to drive a tiered, automated response. The public MPSD corpus (4,202 malicious and 4,316 benign scripts) was first subjected to a data-quality audit, which showed that 55.2\% of the malicious files were exact duplicates, that 12 files carried both labels, and that byte-order marks occurred only in benign files. After cleaning, 1,875 malicious and 4,302 benign scripts remained, and the malicious scripts were found to belong to only 816 structural families. Character 3--5-gram TF-IDF features were combined with 33 interpretable statistical and behavioural indicators aligned with MITRE \attck{}, and logistic regression, random forest, histogram gradient boosting and a soft-voting ensemble were compared under family-aware five-fold cross-validation. The ensemble obtained an F1-score of 0.972 and a ROC-AUC of 0.998, detecting 97.4\% of malicious scripts at a false-positive rate of 1\%; a naive random split on the uncleaned data reported 98.8\% for the same measure. Malicious code embedded in long benign scripts emerged as the principal weakness (46.7\% detected), which improved to 96.4\% when comparable samples were added to training, at the cost of a modest increase in false positives. In a replay of 1,233 unseen scripts presented as Windows Event ID 4104 records, the response engine contained 91.2\% of malicious events, wrongly contained 0.23\% of benign events and required a median of 90.7\,ms per event. The results indicate that lightweight, interpretable models combined with a proportionate and human-supervised response policy offer a practical defence against PowerShell-based attacks.

\section{Introduction}
%% =====================================================================

\subsection{Background and Motivation}
PowerShell is a command shell and scripting language built on the .NET runtime that has shipped with Windows since Windows~7 and Windows Server~2008~R2. Administrators rely on it for configuration management, Active Directory maintenance, software deployment and cloud automation. The same characteristics that make it useful for administration, in particular unrestricted access to .NET classes and Win32 APIs, the ability to execute code held only in memory and built-in remoting, are precisely those an adversary requires after obtaining an initial foothold. A short PowerShell command can retrieve a second-stage payload over HTTP, load it by reflection and execute it without writing an executable to disk. Such intrusions are commonly described as \emph{fileless} or \emph{living-off-the-land} attacks, because they rely on software that is already present and trusted on the host~\cite{wueest2017}.

The problem is long-standing. As early as 2016, Symantec reported that 95.4\% of the PowerShell scripts submitted to the Blue Coat sandbox it analysed were malicious~\cite{wueest2016}. MITRE \attck{} catalogues the behaviour as sub-technique T1059.001~\cite{mitre_t1059}, and the 2025 Threat Detection Report of Red Canary identified Command and Scripting Interpreter as the most frequently observed \attck{} technique for the sixth consecutive year~\cite{redcanary2025}. Removing PowerShell altogether is not a realistic option. In June 2022, the US National Security Agency (NSA) and the Cybersecurity and Infrastructure Security Agency (CISA), together with the national cyber security centres of New Zealand and the United Kingdom, advised organisations to retain PowerShell and to configure and monitor it appropriately~\cite{nsa2022}. The recommended controls, which include Script Block Logging, the Antimalware Scan Interface (AMSI), constrained language mode and transcription, generate a large volume of useful telemetry. They do not, however, decide whether a particular script is hostile, and that decision must be taken quickly and at scale if an attack is to be interrupted before it achieves its objective. Machine learning (ML) is well suited to this decision.

\subsection{Relevance in the Current Threat Landscape}
Several developments make an ML-based detection and response capability for PowerShell particularly relevant at present. Obfuscation has become inexpensive and automated: freely available frameworks such as Invoke-Obfuscation can transform a single command into a very large number of syntactically different but functionally equivalent variants~\cite{bohannon2016}, which defeats exact-match signatures while leaving statistical regularities that learned models can exploit~\cite{bohannon2017}. Security operations centres are also overloaded; endpoint products raise far more alerts than analysts can examine, and alert fatigue is a recognised cause of missed intrusions~\cite{hassan2019}. A calibrated risk score allows low-risk events to be handled automatically and concentrates analyst attention where it is most needed. Finally, generative AI has begun to influence both offence and defence. Large language models (LLMs) have been evaluated for de-obfuscating real malware droppers~\cite{patsakis2024} and for explaining why a PowerShell script is malicious~\cite{wang2026}, but their cost and latency mean that fast classical detectors remain necessary as a first-line filter. Current incident-response guidance further treats detection and response as an integral part of cybersecurity risk management~\cite{nist2025}, which favours systems that link a detector to a documented and auditable response policy.

\subsection{Problem Statement}
Given the text of a PowerShell script block captured on a Windows endpoint, the system should (i)~estimate the probability that the script is malicious with a false-positive rate that is acceptable in production, and (ii)~select a proportionate response automatically, ranging from logging the event to terminating the process and isolating the host, while leaving the most disruptive actions under human control. The solution should operate on static text only, because executing unknown scripts in order to observe their behaviour is slow and hazardous, and its evaluation should reflect performance on scripts that are genuinely new to the model.

\subsection{Objectives}
The objectives of this case study are:
\begin{enumerate}
  \item to audit a public labelled PowerShell corpus for duplicates, label conflicts and spurious artefacts before any model is trained;
  \item to engineer features that capture both lexical patterns and behavioural intent, and to map the behavioural features to MITRE \attck{} techniques;
  \item to train and compare several classifiers under an evaluation protocol that prevents near-duplicate scripts from appearing in both training and test data;
  \item to design a policy-driven response engine that converts a risk score into graded actions and records every decision in an audit log; and
  \item to measure detection quality, response outcomes and processing latency, and to analyse the limitations of the approach.
\end{enumerate}

\subsection{Contributions}
This work contributes, first, a data-quality audit of the MPSD corpus~\cite{fang2021} that quantifies exact duplication, label conflicts and a byte-order-mark artefact that a classifier could exploit as a shortcut. Second, it introduces a family-aware evaluation protocol based on structural skeleton hashing, under which the 1,875 unique malicious scripts form 816 families and each family is confined to a single cross-validation fold. Third, it develops a hybrid detector that combines character n-gram TF-IDF features with 33 interpretable statistical and \attck{}-aligned behavioural indicators, and compares it with single-view baselines. Fourth, it identifies malicious code embedded in benign scripts as the main weakness of models trained on standalone samples and evaluates a leakage-free mitigation. Fifth, it implements a tiered response engine that consumes Windows Event ID 4104 records, attaches \attck{} context, plans containment actions and requires analyst approval before host isolation, and evaluates the complete detection-to-response loop on unseen data.

Section~\ref{sec:method} describes the methodology, Section~\ref{sec:impl} the implementation, and Section~\ref{sec:results} presents and discusses the experimental results. Section~\ref{sec:conc} concludes the report and outlines future work.

\section{Literature Review}\label{sec:lit}
%% =====================================================================

\subsection{PowerShell as an Attack Vector and Defensive Telemetry}
From version 5.0 onwards, PowerShell includes several features intended for defenders. Script Block Logging records the text of every script block compiled by the PowerShell engine in the Microsoft-Windows-PowerShell/Operational log as Event ID 4104~\cite{ms_logging}. Because logging takes place at compilation time, code that is generated at run time, for example a string that is decoded and then passed to \texttt{Invoke-Expression}, is also recorded in its decoded form. AMSI allows any registered anti-malware engine to inspect a script buffer immediately before execution and to block it~\cite{ms_amsi}. Both mechanisms are recommended in the joint NSA/CISA guidance~\cite{nsa2022}. On the analysis side, the \attck{} knowledge base provides a common vocabulary for adversary tactics and techniques~\cite{strom2018}, and it is used in this work to describe what a detected script attempts to do. Industry reports have documented the abuse of PowerShell for almost a decade, describing its use for payload delivery, lateral movement and reconnaissance~\cite{wueest2016} and its central role in fileless attack techniques~\cite{wueest2017}; more recent reports continue to rank script interpreters among the most observed techniques~\cite{redcanary2025}.

\subsection{Obfuscation and De-obfuscation}
Bohannon's Invoke-Obfuscation framework demonstrated how easily PowerShell can be disguised at the token, string, encoding and launcher levels~\cite{bohannon2016}. In response, Bohannon and Holmes developed Revoke-Obfuscation, which extracts approximately 4,000 features from the abstract syntax tree (AST) of a script and applies a linear model to determine whether it is obfuscated. They assembled a corpus of 408,000 scripts, of which about 7,000 were manually reviewed and labelled~\cite{bohannon2017}. Their work established that statistical properties of code are considerably more robust than string signatures.

A second line of research attempts to reverse obfuscation before detection. PowerDrive is a multi-stage static and dynamic de-obfuscator that removes obfuscation layers progressively and was used to analyse thousands of real attacks~\cite{ugarte2019}. Li et al.\ proposed a light-weight de-obfuscation technique based on AST subtrees, combined with semantic-aware attack detection~\cite{li2019}, which Xiong et al.\ later generalised~\cite{xiong2022}. PowerDP predicts the obfuscation types applied to a command, recovers the original content through targeted regular-expression replacement and profiles behaviour with multi-label classifiers~\cite{tsai2023}, whereas PowerPeeler performs dynamic de-obfuscation at the instruction level during execution~\cite{li2024}. Patsakis et al.\ evaluated LLMs on PowerShell droppers from the Emotet campaign and found that GPT-4 recovered the hidden download URLs in 69.56\% of cases~\cite{patsakis2024}. Taken together, these studies show that de-obfuscation improves detection but adds processing cost and complexity. In-engine telemetry such as Event ID 4104 already exposes a partially de-obfuscated view at no additional cost, and this is the input assumed in the present work.

\subsection{Machine-Learning-Based Detection}
Hendler, Kels and Rubin conducted one of the first large-scale studies, training character-level convolutional and recurrent networks and a natural-language-processing (NLP) baseline on 66,388 commands collected by Microsoft~\cite{hendler2018}. Their best detector was an ensemble of the NLP model and a convolutional network, because each detected commands that the other missed. In subsequent work they used data obtained through AMSI and contextual embeddings pre-trained on a large unlabelled corpus, reaching a true-positive rate of nearly 90\% at a false-positive rate below 0.1\%~\cite{hendler2020}. Microsoft described the deployment of such deep models in its Defender products~\cite{ms_blog2019}.

Other studies have explored alternative representations. Rusak et al.\ learned embeddings of AST nodes to classify malicious scripts by family~\cite{rusak2018}. Song et al.\ compared token-based and AST-based feature sets with both classical and deep models and reported detection rates of about 98\% after feature optimisation~\cite{song2021}. Mimura and Tajiri showed that word-embedding representations support purely static detection~\cite{mimura2021}. Fang et al.\ combined FastText embeddings with textual, token and AST-node features in a random forest, reporting 98.93\% accuracy on original scripts and 97.76\% on a harder set in which malicious code is inserted into benign scripts; they also released the MPSD dataset used in this study~\cite{fang2021}. Outside PowerShell, Saxe and Berlin showed that character-level models perform well on short security artefacts such as URLs, file paths and registry keys~\cite{saxe2017}. Broader surveys of ML for malware analysis are provided by Ucci et al.~\cite{ucci2019} and Gibert et al.~\cite{gibert2020}. The most recent direction uses LLMs not only to classify scripts but also to localise the responsible code and explain the verdict in natural language~\cite{wang2026}.

\subsection{Methodological Pitfalls in Security Machine Learning}
High reported accuracy does not guarantee practical value. Sommer and Paxson argued that intrusion detection differs from conventional ML tasks because errors are costly, labelled data are scarce and the environment changes continuously~\cite{sommer2010}. Arp et al.\ catalogued ten common pitfalls, including sampling bias, data snooping, spurious correlations and inappropriate performance measures, and confirmed in a study of 30 papers from leading security venues that these pitfalls are widespread~\cite{arp2022}. Pendlebury et al.\ demonstrated that random train/test splits which disregard time and realistic class ratios can substantially overstate the performance of malware classifiers~\cite{pendlebury2019}. For imbalanced problems, Saito and Rehmsmeier recommend complementing ROC analysis with precision-oriented measures~\cite{saito2015}. These findings shaped the evaluation design described in Section~\ref{sec:protocol}: duplicated and near-duplicated scripts constitute a form of data snooping, and the byte-order-mark artefact is a clear example of a spurious correlation.

\subsection{Automated Incident Response}
Security orchestration, automation and response (SOAR) platforms connect detection tools to response actions through playbooks. Islam et al.\ reviewed the academic and grey literature on security orchestration and identified the integration of heterogeneous tools and the automation of repetitive response tasks as its principal aims~\cite{islam2019}. NoDoze reduced false alarms by ranking alerts with the aid of provenance graphs~\cite{hassan2019}, and Hassan et al.\ subsequently showed that linking endpoint alerts into provenance graphs annotated with \attck{} tactics and techniques reduces false alarms and supports analyst triage~\cite{hassan2020}. NIST SP~800-61 Rev.~3 organises incident-response recommendations around the six Functions of the NIST Cybersecurity Framework~2.0 (Govern, Identify, Protect, Detect, Respond and Recover), treating response as part of overall risk management~\cite{nist2025}.

\subsection{Summary and Research Gap}
Table~\ref{tab:lit} summarises representative studies. The literature shows that ML detectors can achieve high accuracy on PowerShell, that obfuscation-resistant statistical features are more valuable than exact strings, and that evaluation choices can substantially inflate reported results. Three gaps remain. Few studies audit their datasets for duplicates and artefacts before reporting results; most work ends at a classification score and does not address how that score should drive a safe automated response; and response decisions are seldom linked to interpretable evidence, such as \attck{} techniques, that an analyst can verify. The present study addresses all three.

\subsection{System Overview}
Figure~\ref{fig:arch} outlines the proposed system. Script-block text is obtained from endpoint telemetry (Event ID 4104 or an AMSI buffer), cleaned and normalised, transformed into two complementary feature views and scored by a trained model. A policy engine maps the risk score and the behavioural evidence to a response tier, and the associated actions are executed (in this study, simulated) and logged. Analyst decisions are fed back into the labelled data used for periodic retraining. The offline part of the pipeline, comprising the data audit, model training, cross-validation and threshold selection, is described in Sections~\ref{sec:data}--\ref{sec:protocol}; the online response logic is described in Section~\ref{sec:policy}.

\subsection{Threat Model and Assumptions}
The adversary is assumed to have already obtained code execution on a Windows endpoint, for example through a phishing attachment or stolen credentials, and to use PowerShell to download tools, inject code, establish persistence, access credentials or open a command channel. The adversary may obfuscate scripts, rename variables and embed malicious code within otherwise legitimate scripts. Script Block Logging or AMSI is assumed to be enabled, with its output reaching the analysis service; attempts to disable logging or security tooling are treated as suspicious in their own right through the defence-evasion indicators of Section~\ref{sec:features}. Attacks that never invoke PowerShell are out of scope, as are white-box adversarial attacks in which the adversary can query or inspect the model in order to craft evasive inputs~\cite{goodfellow2015}; the latter are discussed as a limitation in Section~\ref{sec:limits}.

\subsection{Dataset and Data-Quality Audit}\label{sec:data}
The study uses the public MPSD corpus released by Fang et al.~\cite{fang2021}. It contains 4,202 malicious scripts (\texttt{malicious\_pure}), 4,316 benign scripts (\texttt{powershell\_benign\_dataset}) and 4,202 ``mixed'' malicious scripts, each created by inserting a malicious script into a benign one. The malicious scripts include download cradles, shellcode loaders, reverse shells, credential-theft tools and persistence scripts, while the benign scripts are administrative scripts and modules collected from public repositories.

Following the recommendations of Arp et al.~\cite{arp2022}, the corpus was audited before training. Each script was hashed with SHA-256 after whitespace normalisation and lower-casing. Only 1,875 of the 4,202 malicious files were unique, so that 55.2\% were exact copies of another file; duplicates were removed and each distinct script was retained once. Twelve files, sharing six distinct contents, appeared under both the malicious and the benign label; as their true label cannot be established, all of them were discarded. Finally, none of the malicious files began with a UTF-8 byte-order mark (BOM), whereas approximately 35\% of the benign files did. A classifier could therefore learn the rule ``a BOM indicates a benign script'', which an attacker could exploit by prepending three bytes; the BOM is consequently removed from every file before feature extraction.

Exact de-duplication does not remove near-duplicates. Many malicious scripts are produced by the same generator and differ only in variable names, numeric constants such as port numbers or shellcode bytes, or whitespace. To capture this, each script $d$ is mapped to a structural skeleton
\begin{equation}
  \kappa(d) = \mathrm{SHA256}\Big(\,\mathrm{strip}_{\mathrm{ws}}\big(\mathrm{abs}_{\mathrm{num}}(\mathrm{abs}_{\mathrm{var}}(\mathrm{lower}(d)))\big)\Big),
  \label{eq:skeleton}
\end{equation}
in which $\mathrm{abs}_{\mathrm{var}}$ replaces every variable name by a placeholder, $\mathrm{abs}_{\mathrm{num}}$ replaces decimal and hexadecimal literals by zero and $\mathrm{strip}_{\mathrm{ws}}$ removes all whitespace. Scripts with the same skeleton form a \emph{family}. Under this definition the 1,875 unique malicious scripts belong to only 816 families, whereas the 4,302 benign scripts form 4,292 families. Figure~\ref{fig:dataset} shows the effect of each step.

\subsection{Pre-processing and Normalisation}
Each script is decoded as UTF-8, or as UTF-16 when a UTF-16 BOM is present; any BOM is removed and the text is truncated to 200,000 characters in order to bound processing time for a small number of very large files. For the lexical view the text is further normalised in two ways that preserve its meaning. It is converted to lower case, because PowerShell keywords, cmdlet names and variable names are case-insensitive, and backtick characters are removed, because PowerShell ignores the backtick escape within identifiers, so that a command name interrupted by backticks reduces to its canonical form. Runs of spaces and tabs are collapsed. These inexpensive steps reverse two of the most common token-level obfuscations without executing the script. The statistical features of Section~\ref{sec:features} are computed on the raw text, since properties such as the proportion of upper-case characters and the density of backticks are themselves informative.

\subsection{Feature Engineering}\label{sec:features}
Two complementary views are constructed for every script. The lexical view describes how the code is written, while the statistical and behavioural view describes what the code does and its overall form. The use of complementary views follows the observation of Hendler et al.\ that models built on different representations tend to make different errors~\cite{hendler2018}.

\subsubsection{Character n-gram TF-IDF}
The normalised text is decomposed into overlapping character sequences of length three to five. Character n-grams tolerate renamed variables and partially split strings and require no PowerShell parser. The weight of n-gram $t$ in script $d$ uses sub-linear term frequency and smoothed inverse document frequency~\cite{salton1988}:
\begin{equation}
  w_{t,d} = \big(1 + \ln \mathrm{tf}_{t,d}\big)\left(\ln\frac{1+N}{1+\mathrm{df}_t} + 1\right),
  \qquad \hat{\mathbf{x}}_d = \frac{\mathbf{x}_d}{\lVert \mathbf{x}_d \rVert_2},
  \label{eq:tfidf}
\end{equation}
where $\mathrm{tf}_{t,d}$ is the number of occurrences of $t$ in $d$, $N$ is the number of training scripts, $\mathrm{df}_t$ is the number of training scripts that contain $t$, and $\mathbf{x}_d$ is the vector of weights $w_{t,d}$. Only n-grams that occur in at least three training scripts are retained, up to a vocabulary of 50,000. The vectoriser is fitted within each cross-validation fold on training data only, so that document frequencies never include test scripts.

\subsubsection{Statistical Features}
Twenty-four numerical features describe the overall form of a script: its length and number of lines (log-scaled); the mean and maximum line length; the proportions of alphabetic, digit, upper-case, whitespace and special characters; the densities of backticks, plus signs (used for string concatenation), quotation marks and braces; the length of the longest token; the number of Base64-like blobs (runs of 80 or more Base64 characters); the numbers of URLs and IPv4 addresses; the density and number of distinct variables; the proportion of comment lines; the number of function definitions; the number of comment-based help keywords; and the presence of a \texttt{param()} block. The character-level Shannon entropy~\cite{shannon1948},
\begin{equation}
  H(d) = -\sum_{c \in \Sigma_d} p_c \log_2 p_c ,
  \label{eq:entropy}
\end{equation}
where $p_c$ is the relative frequency of character $c$ in $d$, is included because encoded or compressed payloads have higher entropy than hand-written code. The documentation-related features reflect the observation that administrative scripts are usually written to be maintained by others and therefore contain help blocks, parameters and functions, whereas attack scripts tend to be short, dense and undocumented.

\subsubsection{Behavioural Indicator Groups Aligned with \attck{}}
Nine further features count matches of groups of regular expressions that describe common adversary behaviours (Table~\ref{tab:indicators}); each count is log-scaled. Grouping patterns by behaviour instead of using each keyword as a separate feature keeps the feature space small and stable and, more importantly, provides the response engine with human-readable evidence. When a script is contained, the alert can state, for example, that it combined a download cradle (T1105) with dynamic execution (T1059.001). In total, the statistical and behavioural view comprises 33 features.

\subsection{Classification Models}\label{sec:models}
Four single-view models and one ensemble were compared, all implemented with scikit-learn~\cite{pedregosa2011}. After cleaning, the ratio of malicious to benign scripts is approximately 1:2.3, and every model therefore uses class weights $\alpha_y = n/(2n_y)$, where $n_y$ is the number of training scripts of class $y$.

\paragraph{Logistic regression.} For the high-dimensional, sparse TF-IDF view, logistic regression (LR) is a natural choice: it trains quickly, is resistant to over-fitting under $L_2$ regularisation and its coefficients identify the n-grams that drive a decision. With labels $\tilde{y}_i \in \{-1,+1\}$, the model is obtained by solving
\begin{equation}
  \min_{\mathbf{w},b}\; \tfrac{1}{2}\lVert\mathbf{w}\rVert_2^2 + C \sum_{i=1}^{n} \alpha_{y_i} \log\!\Big(1 + e^{-\tilde{y}_i(\mathbf{w}^{\top}\mathbf{x}_i + b)}\Big),
  \qquad P(y=1 \mid \mathbf{x}) = \sigma(\mathbf{w}^{\top}\mathbf{x} + b),
  \label{eq:lr}
\end{equation}
where $\sigma$ is the logistic function and $C=10$. The same model, applied to the 33 standardised hand-crafted features with $C=1$, serves as an interpretable baseline.

\paragraph{Random forest.} A random forest (RF) of $T=300$ decision trees, each grown on a bootstrap sample with random feature subsets and split by Gini impurity $G = 1 - \sum_k p_k^2$~\cite{breiman2001}, is trained on the hand-crafted features. Its probability estimate is the average of the tree estimates, $\hat{p}_{\mathrm{RF}}(\mathbf{x}) = \frac{1}{T}\sum_{t=1}^{T}\hat{p}_t(\mathbf{x})$. Random forests capture non-linear interactions between features, require no scaling and are robust to outliers such as extremely long scripts.

\paragraph{Histogram gradient boosting.} A boosted tree ensemble (HGB) that bins features into histograms, in the manner of LightGBM~\cite{ke2017}, is included as a strong conventional learner for tabular data.

\paragraph{Soft-voting ensemble.} The final detector averages the malicious-class probabilities of the lexical and behavioural models:
\begin{equation}
  p_{\mathrm{ens}}(\mathbf{x}) = \tfrac{1}{2}\, p_{\mathrm{LR}}^{\text{TF-IDF}}(\mathbf{x}) + \tfrac{1}{2}\, \hat{p}_{\mathrm{RF}}^{\text{hand}}(\mathbf{x}).
  \label{eq:ens}
\end{equation}
Because the two members rely on different evidence, surface character patterns on the one hand and overall form and behaviour on the other, their errors are only weakly correlated. Equal weights were fixed in advance rather than tuned on the evaluation folds, so as to avoid optimistic bias. Deep neural networks were not used: on a corpus of roughly six thousand unique scripts, published results~\cite{song2021,fang2021} indicate that well-engineered classical models are competitive, and they are cheaper to train, faster at inference and easier to explain to an analyst.

\subsection{Evaluation Protocol}\label{sec:protocol}
All models are evaluated by five-fold cross-validation~\cite{kohavi1995} under two protocols. The \emph{naive} protocol, used only for comparison, applies ordinary stratified five-fold cross-validation to the raw corpus including duplicates; it mirrors a common practice in the literature. The \emph{family-aware} protocol, which provides the main results, applies stratified group five-fold cross-validation to the de-duplicated corpus, using the skeleton family of Equation~\eqref{eq:skeleton} as the group. All members of a family are thus assigned to the same fold, and no model is tested on a script whose near-copy it has seen during training.

Predictions on the held-out folds are pooled, so that every script is scored exactly once by a model that did not see it during training. Treating the malicious class as positive, the following measures are reported:
\begin{gather}
  \mathrm{Precision} = \frac{TP}{TP+FP},\qquad
  \mathrm{Recall} = \mathrm{TPR} = \frac{TP}{TP+FN},\nonumber\\
  F_1 = \frac{2\,\mathrm{Precision}\cdot\mathrm{Recall}}{\mathrm{Precision}+\mathrm{Recall}},\qquad
  \mathrm{FPR} = \frac{FP}{FP+TN},
  \label{eq:metrics}
\end{gather}
together with accuracy, the area under the ROC curve (ROC-AUC) and the true-positive rate at a fixed false-positive rate of 1\% (TPR@1\%FPR), obtained by linear interpolation of the ROC curve. The last measure is the most relevant operationally: in a large organisation even a 1\% false-positive rate on benign scripts can produce many alerts per day, so the detection rate at a low and fixed FPR is a more meaningful summary than accuracy~\cite{saito2015,arp2022}.

A third experiment uses the mixed subset of MPSD, in which malicious code is hidden inside a benign script. To avoid leakage, each mixed sample is scored only by the model of the fold that did not contain its malicious parent script. The benign host may have been seen during training with a benign label, which makes the test deliberately demanding. Mixed samples whose malicious parent could not be identified from the file name were excluded.

\subsection{Automated Response Policy}\label{sec:policy}
Detection alone does not stop an attack. The response engine maps the ensemble score $p$ and the set $\mathcal{G}$ of behavioural indicator groups that fired to one of four tiers:
\begin{equation}
  \mathrm{tier}(p,\mathcal{G}) =
  \begin{cases}
    \textsc{Isolate} & \text{if } p \ge 0.95 \text{ and } \mathcal{G}\cap\mathcal{H} \neq \emptyset,\\
    \textsc{Contain} & \text{if } p \ge 0.70 \text{ (and not \textsc{Isolate})},\\
    \textsc{Alert}   & \text{if } 0.30 \le p < 0.70,\\
    \textsc{Allow}   & \text{if } p < 0.30,
  \end{cases}
  \label{eq:tier}
\end{equation}
where $\mathcal{H}$ contains the high-impact groups (Win32 API/injection, credential access and reflection). The tiers follow the principle of proportionality: inexpensive and reversible actions are automated freely, disruptive actions require stronger evidence, and network isolation of a host additionally requires analyst approval. Table~\ref{tab:policy} lists the actions associated with each tier. The thresholds were fixed \emph{a priori} from the operational meaning of each tier rather than tuned on test data; Section~\ref{sec:resp} reports how the out-of-fold scores are distributed relative to them.

Every decision, comprising the score, tier, techniques, indicators of compromise (IOCs) and actions, is written as one JSON record to an append-only audit log. IOCs are defanged (for instance, \texttt{http} becomes \texttt{hxxp} and dots become \texttt{[.]}) so that log entries cannot be followed accidentally. By default the engine operates in a dry-run mode in which every action is marked as simulated, which reflects the way SOAR playbooks are normally validated before being permitted to act~\cite{islam2019}.

\subsection{Ethical and Safety Considerations}
All malicious samples were handled purely as text and were never executed. The dataset is obtained from its public source at run time and is not redistributed with the project code. IOCs are defanged in all outputs and are omitted from this report. The response engine cannot perform a real action unless dry-run mode is explicitly disabled, and host isolation always requires human approval, consistent with the principle that automated defences should fail safely and remain accountable to people~\cite{nist2025}.

\begin{algorithm}[htbp]
\caption{Processing of one script-block event by the response engine}\label{alg:response}
\begin{algorithmic}[1]
\Require event $e$ with fields \textit{ScriptBlockText}, \textit{ScriptBlockId}, \textit{Computer}, \textit{ProcessId}, \textit{Path}; trained model $M$; policy thresholds
\Ensure decision record appended to the audit log
\State $t_0 \gets$ current time

\EndIf

\If{$\tau = \textsc{Isolate}$}
  \State flag the decision as requiring analyst approval
\EndIf

\end{algorithmic}
\end{algorithm}

\subsection{Deployment on Windows Endpoints}
In a production deployment, Script Block Logging is enabled through Group Policy (Administrative Templates, Windows Components, Windows PowerShell, \emph{Turn on PowerShell Script Block Logging})~\cite{ms_logging}. Event ID 4104 records are forwarded to a central collector by Windows Event Forwarding or an endpoint agent. Windows splits large scripts across several 4104 events that share a \textit{ScriptBlockId} and carry \textit{MessageNumber} and \textit{MessageTotal} fields, so the collector reassembles them before scoring. The trained pipeline is serialised and served behind an internal interface, and the action stubs of the response engine are connected to the organisation's endpoint detection and response (EDR) platform, firewall and ticketing system. Because AMSI exposes the same script content immediately before execution~\cite{ms_amsi}, the model could also be invoked from an AMSI provider in order to block high-confidence scripts before they run rather than respond afterwards.

\subsection{Verification}
Seven unit tests verify that normalisation folds case and backticks; that the feature vector has the expected dimension and finite values; that the indicator groups fire on a typical download cradle but not on a documented administrative function; that two scripts differing only in variable names share a skeleton; that the policy assigns the correct tier for given scores; that isolation is selected only in the presence of a high-impact technique and is flagged for approval; and that IOC defanging behaves as specified. All tests pass.

\subsection{Effect of the Data-Quality Audit}
The audit altered the experimental setting before any model was trained. Of the 8,518 raw files, 2,329 exact duplicates and 12 conflicting files were removed, leaving 1,875 malicious and 4,302 benign scripts. The class balance therefore changed from approximately 1:1 in the raw corpus to approximately 1:2.3. More importantly, the 1,875 unique malicious scripts belong to only 816 structural families, so that each malicious template appears on average 2.3 times with cosmetic differences. A split that distributes such families across training and test folds allows a model to succeed by recognising near-copies rather than by learning what makes a script malicious. Section~\ref{sec:proto} quantifies this effect.

Lexical features constitute the strongest single view: TF-IDF + LR achieves the highest F1 (0.974) and ROC-AUC (0.9986). Logistic regression on the same features is clearly weaker (F1 0.957, 88 false positives), which indicates that interactions between features, captured by trees but not by a linear decision boundary, are important.

The ensemble exchanges a small amount of recall for fewer false alarms. At the default threshold it produces 30 false positives compared with 37 for the lexical model, at the cost of 13 additional false negatives, so that the two F1-scores are almost identical (0.972 and 0.974). The ensemble was nevertheless retained as the detector behind the response engine for two reasons. False positives are what make automated containment costly, since each one may terminate a legitimate administrative task, so the model with the fewest false alarms at a competitive detection rate is preferable. In addition, the random-forest member provides behavioural evidence that can be explained to an analyst more readily than a large set of n-gram weights. Across the five folds, the F1-score of the ensemble ranged from 0.945 to 0.994 (mean 0.972, standard deviation 0.017); the variation arises mainly from which malicious families fall into each test fold.

\subsection{Effect of the Evaluation Protocol}\label{sec:proto}
Table~\ref{tab:proto} and Figure~\ref{fig:proto} compare the two protocols. Under the naive protocol, in which duplicates are retained and folds are random, every model appears better: the F1-score increases by between 0.014 and 0.024, and the TPR@1\%FPR of the ensemble rises from 97.39\% to 98.83\%. The absolute differences appear small, but they conceal a large relative difference in errors. The proportion of malicious scripts missed by the ensemble is 3.84\% under the family-aware protocol and 1.69\% under the naive one, so a naive evaluation would understate the miss rate on genuinely new attacks by a factor of about 2.3. This is consistent with the warnings of Arp et al.~\cite{arp2022} and Pendlebury et al.~\cite{pendlebury2019}, and it suggests that results reported on MPSD with random splits should be interpreted with this effect in mind.

\subsection{Malicious Code Embedded in Benign Scripts}
The mixed subset of MPSD represents a realistic evasion strategy in which a payload is hidden inside a long, legitimate-looking administrative script. In total, 4,064 mixed scripts were evaluated; 138 were excluded because their malicious parent could not be identified. As shown in the first columns of Table~\ref{tab:mixed}, every model trained on standalone scripts detected only 41--53\% of the embedded payloads at the default threshold, the ensemble detecting 46.7\%. This is the most significant weakness revealed by the study. Its cause follows from the interpretability analysis in Section~\ref{sec:interp}: the strongest signals are the overall form of a script and, for the lexical model, its length-normalised n-gram profile. When a few lines of malicious code are surrounded by hundreds of lines of neatly formatted administrative code, both views are dominated by the benign host. Hand-crafted LR performs best in this setting (53.4\%), because its indicator counts contribute additively rather than being overridden by form-based splits as in the tree models.

To mitigate the weakness, and following Fang et al., who included mixed scripts in training~\cite{fang2021}, the training folds were augmented with mixed samples. To prevent leakage, a mixed script was added to the training data of fold $k$ only if both its malicious parent and its benign host belonged to the training folds; on average 2,591 scripts were added per fold. Mixed scripts whose malicious parent lay in fold $k$ were again held out for testing. As Table~\ref{tab:mixed} and Figure~\ref{fig:mixed} show, augmentation raised the detection rate of the ensemble on embedded payloads from 46.7\% to 96.4\%, with 98.3\% of these samples reaching at least the \textsc{Alert} tier; HGB achieved the highest rate (97.4\%). The cost is a modest increase in false alarms on ordinary scripts: the false-positive rate of the ensemble rose from 0.70\% to 1.05\% and its F1-score fell from 0.972 to 0.969. Having seen benign host code inside samples labelled malicious, the model becomes slightly more suspicious of similar benign scripts. Because the tiered policy routes borderline scores to \textsc{Alert} rather than to automatic containment, this trade-off is considered acceptable, and mixed-aware training is recommended for deployment, subject to re-measuring the false-positive rate on local data.

\subsection{Interpretability}\label{sec:interp}
Figure~\ref{fig:imp} lists the most influential hand-crafted features of the random forest. The five most important are the whitespace ratio, the number of lines, the special-character ratio, the mean line length and the digit ratio, all of which describe the form of the code rather than particular commands. The interpretation is straightforward: malicious scripts in the corpus are typically dense one-liners or short blocks with long lines, little indentation, many special characters and long runs of digits, for example shellcode stored as byte arrays, whereas administrative scripts are spread over many short, indented lines. The first behavioural feature, the Win32 API/injection indicator group, ranks eighth. The dominance of form-related features has two sides. Such features are inexpensive and effective, but an attacker can alter them simply by reformatting the code or wrapping it in a long benign script, which is precisely the weakness examined in the previous subsection.

The lexical model provides a complementary and more behavioural explanation. Among its largest positive coefficients are n-grams such as ``\texttt{iex}'', ``\texttt{(new-}'', ``\texttt{w-ob}'', ``\texttt{.exe}'' and ``\texttt{dow}'', which are fragments of the Invoke-Expression alias, of New-Object, of executable file names and of download methods. The strongest benign n-grams, such as ``\texttt{name}'' and sequences of a brace followed by a variable, reflect well-structured code blocks and named parameters. For an analyst, however, the most useful explanation is the list of \attck{} techniques attached to every alert by the response engine, because it describes behaviour rather than model internals. Model-agnostic attribution methods such as SHAP~\cite{lundberg2017} could provide per-script explanations in a future version.

\subsection{Error Analysis}
The 30 false positives and 72 false negatives of the ensemble were examined in aggregate, without reproducing their content, and two distinct patterns emerged. The false positives are long, dual-use tools. Their median length is 47,580 characters, more than twenty times that of a typical benign script, and on average 3.13 indicator groups fire per script, compared with 0.32 for correctly classified benign scripts; 70\% use reflection and 63\% call Win32 APIs. Their function names reveal code-signing helpers, memory and logon-session inspection utilities, DLL-loading wrappers and penetration-testing modules that the dataset labels as benign. Such scripts are genuinely ambiguous, since the same code that an administrator uses for diagnostics is used by attackers for injection.

The false negatives, by contrast, resemble ordinary administration. They contain few behavioural indicators (1.36 groups on average, with 21\% triggering none). Typical examples write registry values, create a scheduled task with an innocuous name, collect the user and host name, or build strings from character codes. Whether such actions are malicious depends on context, such as who ran them, from where and what followed, which is not visible in the script text alone. The tiered policy mitigates both types of error: 45.8\% of the missed malicious scripts still score at least 0.30 and therefore raise an \textsc{Alert} instead of passing silently, while 60\% of the false positives fall below the \textsc{Contain} threshold and generate only a ticket. Adding context from process ancestry or network telemetry, as in provenance-based triage~\cite{hassan2019,hassan2020}, is the most promising way of reducing both error types further.

The replay used the base ensemble trained on standalone scripts and therefore measures the response loop on ordinary scripts; the embedded-code case was examined above. Table~\ref{tab:compare} places the results alongside published work. \subsection{Limitations and Threats to Validity}\label{sec:limits}
Several limitations should be noted. MPSD is a single public corpus with a limited number of malicious families, and its benign scripts come mainly from public repositories; enterprise environments contain in-house scripts that may look different, so the false-positive rate must be re-measured on local data before deployment. The scripts carry no reliable timestamps, which prevented a temporal split of the kind recommended by Pendlebury et al.~\cite{pendlebury2019}; family-aware splitting addresses near-duplicates but not concept drift. The detector sees only script text, whereas context such as the parent process, user, network connections and command-line arguments, which EDR products collect, would help with the ambiguous cases identified in the error analysis. An adversary able to query the model could search for variants that lower the score~\cite{goodfellow2015}; using AMSI or Event ID 4104 output, which already removes several obfuscation layers, combining lexical and behavioural evidence and keeping thresholds conservative reduce this risk without eliminating it. Finally, response actions were simulated in dry-run mode on synthetic event metadata, so the operational cost of terminating processes or isolating hosts in a production network was not measured.

%% =====================================================================
\section{Conclusion and Future Work}\label{sec:conc}
%% =====================================================================
This case study set out to build and evaluate an AI-based system that detects malicious PowerShell scripts and responds to them automatically, while assessing its performance realistically. A careful audit of the MPSD corpus proved essential: more than half of the malicious files were duplicates, a small number of files carried contradictory labels, byte-order marks offered a spurious shortcut, and the remaining malicious scripts formed only 816 structural families. Under a family-aware evaluation that respects these properties, a lightweight ensemble of a character n-gram logistic-regression model and a random forest on 33 interpretable features achieved an F1-score of 0.972, a ROC-AUC of 0.998 and a true-positive rate of 97.39\% at a 1\% false-positive rate. A naive random split would have understated the miss rate by a factor of about 2.3, which is a caution for comparisons with published results. The study also revealed a clear weakness: malicious code hidden in long benign scripts evaded models trained on standalone samples about half of the time, because whole-script form features are diluted by the benign host. Adding such examples to training raised the detection of embedded payloads to 96.4\%, at the cost of a small increase in false positives on ordinary scripts.

Detection was then linked to action. The tiered response engine consumes the Event ID 4104 records that Windows already produces, attaches \attck{} techniques and defanged indicators to every decision, and scales its response from logging to process termination, quarantine and network blocking, with host isolation reserved for analyst approval. In a replay of unseen scripts it contained 91.2\% of malicious events, wrongly contained 0.23\% of benign events and required a median of 90.7\,ms per event. These results indicate that interpretable machine learning combined with a proportionate and auditable response policy is a practical means of defending against living-off-the-land PowerShell attacks, consistent with current guidance to retain PowerShell while monitoring it closely~\cite{nsa2022,nist2025}.

Several extensions would strengthen the system. It should be validated on enterprise telemetry with a temporal split in order to measure concept drift, and retrained periodically using analyst feedback. Scoring individual functions and script blocks in addition to the whole script would prevent a small malicious section from being diluted by a large benign host. AST-based features and pre-trained code embeddings~\cite{hendler2020,fang2021} could be compared with the present features under the same family-aware protocol. Integrating the model as an AMSI provider would allow high-confidence scripts to be blocked before execution. Process-tree and network context from EDR provenance graphs could resolve the dual-use cases that account for most errors~\cite{hassan2020}. An LLM could act as a second-stage assistant that explains \textsc{Alert}-tier scripts in natural language~\cite{wang2026}, with the fast classical model retained as the first-line filter. Finally, robustness against adaptive adversaries should be evaluated and improved through adversarially augmented training.
