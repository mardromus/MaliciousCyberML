\section*{Abstract}
%% ---------------------------------------------------------------------
PowerShell is a scripting tool that comes with every Windows computer. Attackers often use it because it is trusted, powerful and can run code directly in memory without leaving files on disk. This case study examines how PowerShell has been used in real attacks, including the Odinaff attacks on banks, the POSHSPY backdoor of the APT29 group, the Emotet malware campaigns and the REvil ransomware attack through Kaseya VSA. These cases show that traditional signature-based antivirus finds it hard to catch such scripts, because attackers can easily change the text of a script while keeping its behaviour the same. Based on the lessons from these cases, we built and tested a machine-learning system that reads a PowerShell script, decides whether it is malicious, and takes an automatic response according to its risk. Using the public MPSD dataset, from which more than half of the malicious files had to be removed as duplicates, an ensemble model achieved an F1-score of 0.972, detecting 96.2\% of malicious scripts while wrongly flagging only 0.7\% of benign scripts. In a test on unseen scripts, the automatic response system contained 91.2\% of malicious scripts and wrongly blocked only 0.23\% of benign ones. The study shows that explainable machine learning combined with a careful, human-supervised response policy can help organisations defend against PowerShell attacks.

\vspace{0.3cm}
\noindent\textbf{\color{navy}Keywords:} PowerShell, fileless malware, case study, machine learning, malware detection, automated incident response, ransomware, MITRE \attck{}.

\section{Introduction}
%% ---------------------------------------------------------------------
PowerShell is a command-line shell and scripting language made by Microsoft. It is installed by default on Windows and is used by system administrators to automate everyday tasks such as managing users, installing software and changing settings. Because it is powerful and already trusted on the system, attackers also like to use it. With a single PowerShell command, an attacker can download harmful code from the internet and run it directly in memory, without saving any file on the disk. This type of attack is called a \emph{fileless} or \emph{living-off-the-land} attack, because the attacker uses tools that are already present on the computer~\cite{wueest2017}.

PowerShell attacks remain a serious and current problem. Symantec reported that 95.4\% of the PowerShell scripts submitted to its analysis service were malicious~\cite{wueest2016}. MITRE \attck{}, a widely used knowledge base of attacker behaviour, lists PowerShell as technique T1059.001 and records its use by many criminal and state-sponsored groups~\cite{mitre_t1059}. The 2025 Threat Detection Report by Red Canary found that command and scripting interpreters were the most common attack technique for the sixth year in a row~\cite{redcanary2025}. Removing PowerShell is not possible, because organisations depend on it; in 2022 the NSA and CISA advised organisations to keep PowerShell but to log and monitor it carefully~\cite{nsa2022}.

Logging alone, however, only collects data. Someone still has to decide whether each script is safe or harmful, and do so quickly enough to stop an attack. Attackers make this harder by disguising their scripts with free tools such as Invoke-Obfuscation~\cite{bohannon2016}, and security teams already receive more alerts than they can check~\cite{hassan2019}. Machine learning can help by scoring every script automatically and supporting a fast and consistent response, in line with current incident-response guidance~\cite{nist2025}.

\head{Problem statement.} Given the text of a PowerShell script captured on a Windows computer, the system should (1) decide whether the script is malicious, with very few false alarms, and (2) automatically take a suitable action, such as raising an alert or blocking the script, while leaving the most serious actions to a human analyst.

\head{Objectives.} The objectives of this case study are:
\begin{enumerate}
  \item to study how PowerShell has been used in real attacks and what defenders can learn from them;
  \item to review existing research on detecting malicious PowerShell;
  \item to build and compare machine-learning models that detect malicious scripts;
  \item to design an automated response that acts according to the risk of each script; and
  \item to evaluate the system and relate its results back to the real-world cases.
\end{enumerate}

\section{Case Study: PowerShell in Real-World Attacks}
%% ---------------------------------------------------------------------
This section looks at why attackers choose PowerShell, how a typical attack unfolds, and what four well-documented incidents teach defenders.

\head{Why attackers choose PowerShell.} PowerShell offers attackers several advantages at once. It is already installed and trusted, so running it does not look unusual. It can call almost any Windows function and .NET library, which allows it to download files, read passwords, change security settings and talk to remote servers. It can run code that exists only in memory, which leaves little evidence on disk for antivirus to scan. Finally, scripts can be encoded or disguised in many ways, so the same attack can look completely different each time~\cite{wueest2016,bohannon2016}. In earlier years, detailed PowerShell logging was also turned off by default in most organisations, so attackers could often act without leaving a record~\cite{wueest2016}.

\head{A typical attack chain.} Figure~\ref{fig:chain} shows how PowerShell commonly appears in an attack. The attacker first gains entry, often through a phishing email with a malicious document. When the victim opens the document, a hidden macro starts PowerShell, which downloads the next stage of the attack (\attck{} T1105) and runs it in memory (T1059.001, T1620). The attacker then sets up a way to come back later (persistence), steals passwords (T1003), turns off security tools (T1562) and spreads to other computers. The final goal may be data theft, financial fraud or ransomware. PowerShell can be involved at almost every stage, which means that monitoring it gives defenders many chances to stop the attack.

\head{Case 1: Odinaff attacks on financial organisations (2016).} In 2016, Symantec reported a series of targeted attacks on banks, securities and trading firms and payroll companies around the world, carried out with a trojan called Odinaff~\cite{symantec2016odinaff}. The trojan was delivered through malicious Word macros, password-protected archives and existing botnets. Once inside a network, the attackers used lightweight hacking tools such as Mimikatz together with legitimate utilities such as PowerShell to move between computers and find important systems; some victims were users of the SWIFT interbank messaging system. This case shows how criminals combine PowerShell with password-stealing tools to explore a network quietly, because activity by a legitimate administration tool does not raise suspicion on its own.

\head{Case 2: APT29 and the POSHSPY backdoor (2015--2017).} Mandiant described POSHSPY, a backdoor used by the state-sponsored group APT29 as a secret fallback in case its main tools were discovered~\cite{dunwoody2017}. POSHSPY was built entirely from PowerShell and Windows Management Instrumentation (WMI). Its encrypted PowerShell code was stored inside a custom WMI property instead of a file, and a WMI event subscription restarted it automatically. It could download and run more PowerShell code and programs, and it contacted its servers rarely and through legitimate local websites. Mandiant noted that, because only legitimate system processes were used, the malicious activity could be identified only through enhanced logging or memory analysis. This case shows the importance of PowerShell logging: without it, a fileless backdoor can stay hidden for long periods.

\head{Case 3: Emotet malware campaigns (2014 onwards).} Emotet started as a banking trojan and became one of the most widespread malware families in the world, often delivering other malware such as ransomware. In October 2020, CISA warned of a large increase in Emotet phishing emails targeting state and local governments, noting that Emotet spreads through networks by guessing passwords and copying itself to shared drives~\cite{cisa2020emotet}. Many Emotet campaigns used Word documents whose macros launched an obfuscated PowerShell command to download the malware. Patsakis et al.\ studied such PowerShell droppers from real Emotet campaigns and found them heavily disguised, so that even advanced language models could not always recover the hidden download addresses~\cite{patsakis2024}. This case shows that obfuscation is used at large scale and that defences based on fixed strings are easily bypassed.

\head{Case 4: REvil ransomware through Kaseya VSA (2021).} On 2 July 2021, an affiliate of the REvil ransomware group exploited Kaseya VSA, a remote management tool used by managed service providers, and pushed a malicious update to their customers, affecting hundreds of businesses in a single day~\cite{sophos2021}. Because the management agent ran with high privileges, the attackers used a PowerShell command to switch off Microsoft Defender's real-time protection and script scanning before deploying the ransomware~\cite{splunk2021}. This case shows how quickly modern attacks can spread: a single malicious update reached hundreds of businesses on the same day, leaving little time for manual investigation. It also shows that a script trying to disable security tools is itself a strong warning sign.

\head{Comparing the cases.} Although the four incidents had different goals, they share a common pattern. The attackers were of very different types: a financially motivated criminal group (Odinaff), a state-sponsored espionage group (APT29), a large criminal malware operation (Emotet) and a ransomware affiliate (REvil). Their priorities also differed. APT29 valued stealth and long-term access, so POSHSPY was designed to run rarely and to blend in with normal traffic. REvil valued speed and scale, so its PowerShell activity was short and direct, focused on disabling defences just before the ransomware ran. Emotet relied on volume, sending very large numbers of emails with disguised scripts, while Odinaff relied on careful exploration of a small number of selected networks. In every case, however, PowerShell was chosen because it was already present, trusted and capable, and in every case the malicious activity left traces in the scripts that ran. Mapped onto Figure~\ref{fig:chain}, Emotet appears mainly at the execution and download stages, APT29 at the in-memory payload and persistence stages, Odinaff at the credential-theft and network-exploration stages, and REvil at the defence-evasion stage just before impact. A defensive system that examines every script, instead of looking for one particular tool or stage, therefore has a chance to interrupt very different kinds of attack.

The table also shows a gap: logging and scanning produce evidence, but none of these controls by itself decides quickly whether a particular script is malicious and what to do about it. \head{Lessons from the cases.} Table~\ref{tab:cases} summarises the four cases. Together they lead to five requirements for a defensive system, which guide the rest of this study:
\begin{enumerate}
  \item \textbf{Use the logs Windows already produces.} Script Block Logging and AMSI record the actual code that runs, including code that was hidden or downloaded at run time~\cite{ms_logging,ms_amsi}.
  \item \textbf{Look at behaviour, not exact text.} Because scripts are easily disguised, detection should use patterns that survive small changes.
  \item \textbf{Keep false alarms very low.} Administrators use PowerShell every day, so a detector that blocks legitimate work will not be trusted.
  \item \textbf{Respond automatically and quickly.} Ransomware can spread very quickly, so routine actions must happen without waiting for a person.
  \item \textbf{Explain every decision.} Alerts should say what the script was trying to do, for example in \attck{} terms~\cite{strom2018}, so analysts can act on them.
\end{enumerate}

\section{Literature Review}
%% ---------------------------------------------------------------------
Microsoft has added security features to PowerShell that make detection possible. \emph{Script Block Logging} records the text of every script that runs as Windows Event ID 4104~\cite{ms_logging}, and the \emph{Antimalware Scan Interface} (AMSI) allows antivirus software to scan a script just before it runs~\cite{ms_amsi}. The MITRE \attck{} framework provides a common language to describe attacker behaviour~\cite{strom2018}.

Because attackers disguise their scripts, much research has focused on obfuscation. Bohannon showed that a single command can be rewritten in many forms~\cite{bohannon2016}, and Bohannon and Holmes built Revoke-Obfuscation, which detects disguised scripts using statistical features~\cite{bohannon2017}. Several tools try to remove the disguise before analysis, including PowerDrive~\cite{ugarte2019}, the method of Li et al.~\cite{li2019} and its extension by Xiong et al.~\cite{xiong2022}, PowerDP~\cite{tsai2023} and PowerPeeler~\cite{li2024}.

Machine learning has been applied to detect malicious PowerShell directly. Hendler et al.\ trained deep neural networks on more than 66,000 PowerShell commands and found that combining two different models gave the best results~\cite{hendler2018}. In later work they used AMSI data and reached a detection rate of nearly 90\% with less than 0.1\% false alarms~\cite{hendler2020}, and Microsoft described using such models in its Defender products~\cite{ms_blog2019}. Rusak et al.\ used the syntax tree of scripts~\cite{rusak2018}, Song et al.\ compared token-based and tree-based features and reported about 98\% detection~\cite{song2021}, and Mimura and Tajiri used word embeddings~\cite{mimura2021}. Fang et al.\ combined several types of features with a random forest, reported 98.93\% accuracy and released the MPSD dataset used in this study~\cite{fang2021}. Saxe and Berlin showed that character-level models work well for short security texts such as web addresses~\cite{saxe2017}, and general reviews of machine learning for malware are given by Ucci et al.~\cite{ucci2019} and Gibert et al.~\cite{gibert2020}. The newest work uses large language models to both detect and explain malicious PowerShell~\cite{wang2026}.

Researchers have also warned that machine-learning results in security can look better than they really are. Sommer and Paxson explained why intrusion detection is harder than ordinary classification~\cite{sommer2010}. Arp et al.\ listed common mistakes, such as allowing very similar samples to appear in both training and test data~\cite{arp2022}, and Pendlebury et al.\ showed that careless data splitting can make malware detectors appear much more accurate than they are~\cite{pendlebury2019}. On the response side, security orchestration, automation and response (SOAR) tools connect detection to automatic actions~\cite{islam2019}, and provenance-based methods help analysts handle large numbers of alerts~\cite{hassan2019,hassan2020}.

Table~\ref{tab:lit} summarises important studies. Most previous work focuses only on detection and reports very high accuracy, but few studies check their datasets for duplicate samples, and very few connect detection to an automatic response. This case study addresses both gaps.

\section{Methodology}
%% ---------------------------------------------------------------------
The proposed system follows the five requirements identified in the case study. It works in six steps, shown in Figure~\ref{fig:flow}: scripts are collected from Windows logs, the data is cleaned, features are extracted, a machine-learning model gives each script a risk score between 0 and 1, a response policy chooses an action, and every decision is recorded.

\begin{figure}[htbp]
\centering
\begin{tikzpicture}[font=\small,

  \node[box, right=0.9cm of b] (c) {\textbf{3. Extract features}\\ text and behaviour};
  \node[box, below=1.0cm of c] (d) {\textbf{4. ML model}\\ risk score (0--1)};
  \node[box, left=0.9cm of d] (e) {\textbf{5. Response policy}\\ choose an action};
  \node[box, left=0.9cm of e] (f) {\textbf{6. Act and record}\\ alert, block, log};
  \draw[arr] (a) -- (b); \draw[arr] (b) -- (c); \draw[arr] (c) -- (d);

\end{tikzpicture}

\head{Dataset.} We used the public MPSD dataset released by Fang et al.~\cite{fang2021}. It contains 4,202 malicious scripts, 4,316 benign scripts and 4,202 ``mixed'' scripts in which malicious code is hidden inside a normal script. The malicious scripts include downloaders, shellcode loaders, reverse shells and password-stealing tools, similar to those seen in the cases above. The benign scripts are normal administration scripts. All malicious scripts were handled only as text and were never run.

\head{Data cleaning.} Before training, the data was checked for problems, as recommended by Arp et al.~\cite{arp2022}. Only 1,875 of the 4,202 malicious files were unique, which means 55.2\% were exact copies; duplicates were removed. Twelve files appeared in both the malicious and benign folders and were removed because their true label is unknown. A special byte-order mark appeared at the start of about 35\% of benign files but never in malicious files; since a model could learn this meaningless pattern, it was removed from all files. Finally, many malicious scripts differ only in variable names or numbers, so such near-copies were grouped into ``families'' (816 families for 1,875 malicious scripts), and a family was never split between training and testing. After cleaning, 1,875 malicious and 4,302 benign scripts remained.

\head{Feature extraction.} Each script is converted to lower case and the backtick character is removed, because PowerShell ignores both and attackers use them to disguise commands. Two kinds of features are then extracted. The first are \emph{text features}: the script is split into short sequences of 3 to 5 characters, and each sequence is weighted with TF-IDF~\cite{salton1988}, so that a sequence that is frequent in one script but rare in others receives a high weight:
\begin{equation}
  \text{TF-IDF}(t,d) = \text{tf}(t,d) \times \log\frac{N}{\text{df}(t)},
\end{equation}
where $\text{tf}(t,d)$ is how often sequence $t$ appears in script $d$, $N$ is the number of scripts and $\text{df}(t)$ is the number of scripts containing $t$. The second are 33 \emph{behaviour and statistical features}, such as script length, number of lines, randomness of characters and counts of suspicious keywords. The keywords are grouped by attacker behaviour and linked to \attck{}, for example downloading tools (T1105), running code (T1059.001), code injection (T1055) and disabling defences (T1562), which are the same behaviours seen in the case study.

\head{Machine-learning models.} Four models and one ensemble were trained with the scikit-learn library~\cite{pedregosa2011}: logistic regression (LR) on the text features, LR on the behaviour features as a simple baseline, a random forest (RF) of 300 decision trees~\cite{breiman2001}, and a gradient boosting model (HGB) similar to LightGBM~\cite{ke2017}. The ensemble averages the scores of the text-based LR and the behaviour-based RF; because the two look at different evidence, combining them makes the result more stable. Deep learning was not used because the dataset is small and simpler models are faster and easier to explain.

\head{Evaluation.} The models were tested with five-fold cross-validation~\cite{kohavi1995}: the data is split into five parts, and each part is used once for testing while the other four are used for training. Families of near-copies were always kept in the same part, so a model is never tested on a script it has almost seen before. With TP, FP, TN and FN denoting true positives, false positives, true negatives and false negatives, the main measures were:
\begin{equation}
  \text{Precision} = \frac{TP}{TP+FP},\qquad \text{Recall} = \frac{TP}{TP+FN},\qquad F_1 = \frac{2 \times \text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}.
\end{equation}
Accuracy and the area under the ROC curve (AUC) were also reported.

\head{Automated response.} The risk score is used to choose one of four actions (Table~\ref{tab:tiers}). Less harmful actions are taken automatically, while the most serious action, disconnecting a computer from the network, needs a human analyst's approval. Every decision is saved in a log together with the \attck{} techniques found, and suspicious web addresses are written in a safe form (for example, \texttt{hxxp} instead of \texttt{http}).

\section{Implementation Details}
%% ---------------------------------------------------------------------
The system was written in Python 3.13 using scikit-learn for machine learning, pandas and NumPy for data handling and Matplotlib for graphs, and it was run on an ordinary computer with a 4-core processor and 15 GB of memory, without a GPU. The code has four parts: a data module that cleans the dataset, a feature module that calculates the text and behaviour features, a model module that trains and tests the models, and a response module. The response module reads Windows Event ID 4104 records, obtains a risk score from the model, chooses the response level, adds the matching \attck{} technique and writes the decision to a log. For safety, it runs in a test (dry-run) mode in which actions are recorded but not actually carried out. In a real organisation, Script Block Logging would be enabled through Group Policy~\cite{ms_logging}, the logs would be sent to a central server for scoring, and the response module would be connected to the organisation's security tools. Seven unit tests check the main functions, and all of them pass.

\head{Effect of removing duplicates.} When the ensemble was tested on the original data with duplicates and a simple random split, its F1-score rose to 0.988 and the share of missed malicious scripts fell from 3.8\% to 1.7\%. This higher result is misleading, because the model was partly tested on copies of scripts it had already seen. Without cleaning, the number of attacks missed in real use would have been underestimated by more than half, which agrees with the warnings of Arp et al.~\cite{arp2022} and Pendlebury et al.~\cite{pendlebury2019}.

\head{Malicious code hidden inside normal scripts.} The models were also tested on the ``mixed'' scripts, where malicious code is hidden inside a long normal script, a trick similar to the disguised droppers in the Emotet case. This was the main weakness found: the ensemble detected only 46.7\% of these scripts, because the large amount of normal code hides the small malicious part. When examples of mixed scripts were added to the training data, detection rose to 96.4\%, while false alarms on normal scripts increased only slightly (from 0.70\% to 1.05\%). Training with such examples is therefore recommended.

\head{Automated response results.} To test the complete system, the ensemble was trained on four parts of the data, and the fifth part (1,233 scripts it had never seen) was sent through the response system as Windows log events. Table~\ref{tab:response} shows the outcome. Most malicious scripts were stopped automatically, very few benign scripts were blocked, and a typical script was processed in about 91 milliseconds, which is fast enough to act before an attack like the REvil case can spread. The most common attacker behaviours found were running code with PowerShell (T1059.001), loading code into memory (T1620), code injection (T1055) and downloading tools (T1105), the same stages shown in Figure~\ref{fig:chain}.

\head{Illustrative walkthrough: an Emotet-style infection.} To show how the parts of the system work together, consider an employee who opens an infected invoice document, as in the Emotet campaigns. The following sequence describes the intended behaviour of the system; it is an illustration based on its design, not a recorded incident.
\begin{enumerate}
  \item The document's macro starts PowerShell with an encoded command. Windows decodes the command before running it and records the readable script as Event ID 4104.
  \item The system receives the event within seconds and extracts its features. The encoding indicator (T1027) and the download indicator (T1105) are both present, and the text features match patterns of known downloaders, so the model gives a high risk score.
  \item Because the score is above 0.70, the script is contained: the PowerShell process is stopped, the file is quarantined and the download address is blocked, so the next stage of the malware is never fetched.
  \item The security team receives an alert listing the score, the \attck{} techniques and the blocked address. If signs of code injection or credential theft were also present with a very high score, isolation of the computer would be proposed and would wait for an analyst's approval.
\end{enumerate}
This walkthrough shows how the lessons from the case study (use existing logs, look at behaviour, respond quickly and explain every decision) are reflected in the design of the system.

\head{Limitations.} The study has some limitations. Only one public dataset was used, so the results should be checked again on real company data. The system looks only at the script text and not at other information such as which program started the script, which would help in cases like Odinaff where legitimate tools are misused. Most mistakes were made on scripts that can be used for both good and bad purposes, such as system tools that also use low-level Windows functions. Finally, the response actions were tested in a safe simulation, not on a real network.

%% ---------------------------------------------------------------------
\section{Conclusion}
%% ---------------------------------------------------------------------
This case study examined how PowerShell is used in real attacks and how machine learning can help defend against them. The Odinaff, APT29, Emotet and REvil cases show that attackers use PowerShell at every stage of an attack, disguise their scripts to avoid signatures, and can cause serious damage very quickly. From these lessons, a system was built that scores PowerShell scripts from Windows logs and responds automatically. After removing duplicates and wrong labels from the MPSD dataset, an ensemble of a text-based logistic regression model and a behaviour-based random forest reached an F1-score of 0.972, detecting 96.2\% of malicious scripts with only 0.7\% false alarms. In a test on unseen scripts, the response system stopped 91.2\% of malicious scripts, wrongly blocked only 0.23\% of benign scripts and needed about 91 milliseconds per script. Two further lessons emerged: datasets must be checked for duplicates, otherwise results look better than they are, and malicious code hidden inside normal scripts needs special training examples. In future, the system can be tested on real company logs, connected to AMSI to block scripts before they run, given information about running processes, and combined with large language models that explain alerts to analysts~\cite{wang2026}. Overall, explainable machine learning together with a careful, human-supervised response policy offers a practical defence against PowerShell attacks, in line with expert advice to keep PowerShell but monitor it closely~\cite{nsa2022}.
